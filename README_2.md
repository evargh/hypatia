To run Hypatia in an arbitrary system, I wrote a Dockerfile and a guide in `scratch` on how to do that. If you want to do that, you can—edit any files outside of the container and run all building/debugging commands in the container.

First, build Hypatia according to the `README.md` file given by the authors. These functions have been inspected for correctness and stability through assertions, but exhaustive edge case exploration hasn't been done yet.

To generate the constellation, first refer to the guide in `paper`. However, make the following adjustments:

1. In order to allow for more flexible choices on how to set ISLs, I changed the interface to `generate_plus_grid_isls.py`. This is due to how Hypatia phases satellites—in Hypatia, orbits are assigned indices. Satellites on orbits with even indices are not phased, while satellites on orbits with odd indices are phased by `360/n/2` degrees, where `n` is the number of satellites per orbit. This leads to an (in my opinion) clumsy default Grid+ topology—you can visualize that default by plotting the TLE generated by this code in a constellation viewer (MATLAB has one) and seeing how the links are established. To cope with the fact that satellites are phased depending on orbit parity, I changed the interface so that ISLs are assigned based on orbit parity.
2. To interact with the changed interface in `generate_plus_grid_isls.py`, I changed `main_helper.py`. While the satgenpy regression tests pass, only Starlink-550 was tested with this new ISL configuration. I would test other constellations and check correctness for those as well.
3. When the directories are generated, you will also need to generate a list of "truncated" fstate files. Fstate files in Hypatia have the double role of both enumerating which satellites are accessible to which ground stations, and encompassing all forwarding logic at a time step. Truncated fstate files only enumerate which satellites are accessible to which ground stations. In another sense, they allow ground stations to forward to their shortest-path satellite, but allow satellites to maintain their own routing algorithm. Additionally, truncated fstate files are smaller in size, requiring less disk usage and therefore a faster simulation. To generate this, do the following

a. In your `dynamic_state_<x>_for_<y>` directory, create a new directory `truncated_dir`.
b. Then, run `python3 <path to helper_scripts/create_truncated_fstate.py> <path to dynamic_state_<x>_for_<y> directory> <num satellites in constellation> <y in nanoseconds - x in nanoseconds> <x in nanoseconds>`

Now, you can run the network simulation over these constellations. Follow the guide in `paper`. However, make the following adjustments to ns3:

1. Go to `hypatia/ns3-sat-sim/simulator/contrib/basic-sim/helper/core/tcp-optimizer.cc:51` and set that flag to `false`. Selective ACKs in Hypatia lead to a (seemingly) spurious assertion failure that I was not able to diagnose. Diagnosing this would involve updating the underlying NS3 version, Hypatia itself, and the `basic-sim` module to the most modern versions, and then using either NS3's logging suite or a record-replay debugger to investigate whether these assertions repeated and, if so, when.
2. (Optional) Apply the NS3.32 patch by downloading the patch file from the NS3 website, putting it in the `ns3-sat-sim/simulator` directory, and running the command `patch -p1 < ns-3.31-to-ns-3.32.patch`. This was something I did when attempting to diagnose the SACK bug. However, it did not help. For absolute reproducibility, I'm documenting this.

When following the guide, make the following changes:
3. `step_1_generate_runs.py` is now more flexible in order to accommodate for different experiment types (`step_1_generate_runs_old.py` is the old file). You have multiple `traffic files`, of the format
To create an experiment, do the following:
  a. Run `python3 step_1_generate_runs.py <ISL queue size in packets> <GSL queue size in packets> <traffic matrix> <setting>`
    Other than for weak scaling, the queue sizes were 120 packets for ISLs and 1200 packets for GSLs. This was set by the BDP calculation.
    The traffic matrix options are the following:
      `traffic_pop_gravity_w<x>_<y>s.csv` gives a traffic matrix between 19 cities of 230 flows per second, with total traffic `x*10` Mbps over `y` seconds.
      `traffic_pop_pairwise_w<x>_<y>s.csv` does the same with a traffic matrix between 100 cities with 200 flows per second, with the same total traffic again over `y` seconds.

    The settings are the following:
      <transport protocol>_<traffic type>_<x>s: This allows for running a simulation of x seconds, with logging designed for <traffic type>, and the use of <transport protocol>
      Make sure that the number of seconds for the traffic matrix and the traffic type (gravity or pairwise) match.
      There is an additional setting that mentions "high bandwidth". This was for the weak scaling experiment, and its only change is an increase in the ISL and GSL link capacities.

    To determine the queue lengths, run `python3 <path to helper_scripts/generate_buffer_size_from_altitude_and_isl_bandwidth.py> <link bandwidth in bps> <orbit altitude in km>`. This will tell you how large the buffers need to be according to the BDP scaling rule. (Currently, Hypatia structures its buffers in terms of packets and not bytes. Migrating to bytes instead of packets may be useful for better understanding link behavior, as the queueing delay incurred by a small ACK is different than a large packet with a payload.)

    For example, I ran `python3 step_1_generate_runs.py 120 1200 traffic_pop_gravity_w3.csv tcp_gravity_200s` to generate the plots with 30 Mbps global traffic and 10 Mbps ISL links.

  b. Set the algorithm you want in `ns3-sat-sim/simulator/scratch/main_satnet/main_satnet.cc` by a flag on line 53. The flags are:
      0: Snapshot Routing
      1: DHBP
      2: HBM
      3: INNER
      4: ELB over HBM

  c. Run `export NS_LOG="PointToPointLaserNetDevice=level_debug|prefix_func|prefix_time:GSLChannel=level_debug|prefix_func|prefix_time:ArbiterDhbpSat=level_debug|prefix_func|prefix_time:ArbiterElbSat=level_debug|prefix_func|prefix_time:ArbiterInnerSat=level_debug|prefix_func|prefix_time:GSLNetDevice=level_debug|prefix_func|prefix_time"` in your shell to have the console log everything necessary. *NOTE:* Logging increases the runtime significantly. I think its a disk access/batching issue, but I'm not 100% sure. Run these tests overnight for the five algorithms presented.

  d. Run `step_2_run.py` in the paper directory. After each algorithm finishes, create a folder, and move `console.txt`, `tcp_flows.csv`, `tcp_flows.txt`, and `isl_utilization.csv` to that folder.

  e. You will need to use the following scripts from `paper/helper_scripts`:
      `parse_ingress_traffic_by_satellite.py`
      `parse_flow_times.py`
      `parse_queue_length_timeline.py`

  f. Then, in the folder where you stored the files you got from the experiment, run the following commands:
      `python3 <path to parse_ingress_traffic_by_satellite.py> console.txt 1584 > ingress.json`
      `python3 <path to parse_flow_times.py> tcp_flows.csv`
      `mkdir qt; cd qt; python3 <path to parse_queue_length_timeline.py> ../console.txt`

      These will generate `ingress.json`, `flow_aggregate_times.json`, and `qt`, a folder that stores interface fullness for each satellite.

Repeat this process for each experiment you want to run. The steps for generating the experiments are as follows:
  Set the flag in `main_satnet.cc` line `33` to 0. Run (and store the console, tcp_flows.csv, etc for):
      `python3 step_1_generate_runs.py 120 1200 traffic_pop_gravity_w1.csv tcp_gravity_200s`
      `python3 step_1_generate_runs.py 120 1200 traffic_pop_gravity_w3.csv tcp_gravity_200s`
      `python3 step_1_generate_runs.py 360 1200 traffic_pop_gravity_w1.csv tcp_gravity_200s_high_bandwidth_links`

  Repeat this process for `main_satnet.cc` flag `1,2,3,4`
