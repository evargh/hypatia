First, build Hypatia according to the `README.md` file given by the authors. (may fix) You can run `hypatia_run_tests.sh`, but I expect it to fail. This is because the testing suite has not been updated according to the system extensions (the `fstate` files which store shortest path information have a different format now—this change was made to test an algorithm, but ended up becoming technical debt. This change can actually be reverted: the changes I made can be viewed in [this blame](https://github.com/evargh/hypatia/blame/ff38d85b942e378265147f53e5f98d2085af069f/satgenpy/satgen/dynamic_state/fstate_calculation.py). I did not do this). I **STRONGLY RECOMMEND** fixing the testing suite for integration tests—however, we have different assumptions. This may take some work, but I think is a good way to first figure out how NS3 works.

These functions have been inspected for correctness and stability through assertions, but exhaustive edge case exploration hasn't been done yet.

To generate the constellation, first refer to the guide in `paper`. However, make the following adjustments:

1. In order to allow for more flexible choices on how to set ISLs, I changed the interface to `generate_plus_grid_isls.py`. This is due to how Hypatia phases satellites—in Hypatia, orbits are assigned indices. Satellites on orbits with even indices are not phased, while satellites on orbits with odd indices are phased by `360/n/2` degrees, where `n` is the number of satellites per orbit. This leads to an (in my opinion) clumsy default Grid+ topology—you can visualize that default by plotting the TLE generated by this code in a constellation viewer (MATLAB has one) and seeing how the links are established. To cope with the fact that satellites are phased depending on orbit parity, I changed the interface so that ISLs are assigned based on orbit parity.
2. To interact with the changed interface in `generate_plus_grid_isls.py`, I changed `main_helper.py`. However, only Starlink-550 was tested with this new ISL configuration. I would test other constellations and check correctness for those as well.

To run the network simulation over these constellations, follow the guide in `paper`. However, make the following adjustments:

1. Go to `hypatia/ns3-sat-sim/simulator/contrib/basic-sim/helper/core/tcp-optimizer.cc:51` and set that flag to `false`. Selective ACKs in Hypatia lead to a (seemingly) spurious assertion failure that I was not able to diagnose in a timely manner. Diagnosing this would involve updating the underlying NS3 version, Hypatia itself, and the `basic-sim` module to the most modern versions, and then using either NS3's logging suite or a record-replay debugger to investigate whether these assertions repeated and, if so, when.
2. (Optional) Apply the NS3.32 patch with the command `<>`. This was something I did when attempting to diagnose the SACK bug. However, it did not help. For absolute reproducibility, I'm documenting this.

In order to generate a run, you need a traffic file (contact Xiaojuan for this code), an NS3 configuration file, and some constellation-specific knowledge.
To determine the queue lengths, solve the following formula: <link bandwidth in bytes> * (6378+<satellite altitude in km>)*2000*math.pi/2/300000000 = buffer capacity in bytes
Currently, Hypatia structures its buffers in terms of packets and not bytes. Migrating to bytes instead of packets may be useful for better understanding link behavior, as the queueing delay incurred by a small ACK is different than a large packet with a payload.

Table 6.2:
To calculate the DHBP overhead:
Run `grep -rIi "PointToPointLaserNetDevice:Receive" <dhbp console file> | wc -l` to get the number of times a satellite received a packet (a)
Run `grep -rIi "PointToPointLaserNetDevice:Send" <dhbp console file> | wc -l` to get the number of times a satellite sent a packet (b)
Run `grep -rIi "GSLChannel:TransmitTo" <dhbp console file> | wc -l` to get the number of times a satellite transmitted to or received from a ground station (c)

Find the sum of (a) and (b), then run `python3 calculate_overhead_dhbp.py --num-isl-transcieves <a+b> --num-gsl-transcieves <c> --total-traffic-kb <total amount of traffic in kilobytes>`, where the third argument is the total amount of traffic across the whole simulation, not per second. For example, 30 Mbps global traffic per second really means 30\*1000\*200 total kilobytes of traffic across the simulation.

To calculate the ELB overhead:
Run `grep -rIi "congestion change to beta" <elb console file> | wc -l` to get the number of times a node reported that it's in the busy state (a)
 Run `grep -rIi "congestion change to alpha" <elb console file> | wc -l` to get the number of times a node reported that it's entering FBS (b)
Run `grep -rIi "congestion change to uncongested" <elb console file> | wc -l` to get the number of times a node reported that it's uncongested (c)

Find the sum of (a) and (b), then run `python3 calculate_overhead_dhbp.py --num-beta-messages <a> --num-non-beta-messages <b+c> --total-traffic-kb <total amount of traffic in kilobytes>`, where the third argument is the same as for DHBP.

To calculate the INNER overhead:

Run `grep -rIi "congested" <inner console file> | wc -l` to get the number of times a node reported that an interface is congested (a)

Run `python3 calculate_overhead_inner.py --num-congestion-messages <a> --total-traffic-kb <total amount of traffic in kilobytes>`
